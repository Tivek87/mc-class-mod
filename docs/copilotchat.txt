However, there is an important limit:

The larger the custom engine becomes, the more it will fight Minecraft’s own systems.

Minecraft already controls:

The main game loop
World rendering
Entities
Physics
Chunks
Lighting
Resource loading
Networking
Mod lifecycle
So there are two possible directions:

1. Bigger Minecraft-based engine
Keep using Minecraft and improve the mod’s internal systems. This is realistic and could support very advanced abilities, characters, effects, and custom gameplay.

2. Fully independent engine
Eventually remove the Minecraft dependency and create an engine with its own:

Window system
Renderer
World format
Physics
Entity system
Asset pipeline
Networking
Editor
That would be a much larger project—closer to building a new game engine like a small Unity or Godot.

Best approach: keep Minecraft as the base and turn the existing code into a clean, modular “superpower engine.” The current ConstructPainter, Mesh, SpellCasting, payload networking, and character systems are good starting points for that.

Wat moet je in Claude’s rules zetten?
Zet niet alleen visuele wensen in de rules. Zet vooral vaste technische contracten erin.

Aanbevolen regels
Text
## Architecture rules

- Server owns gameplay truth: damage, cooldowns, targets, movement authority,
  costs and permissions.
- Client owns presentation: rendering, HUD, particles, camera effects and
  interpolation.
- Every ability must have explicit start, tick, stop and cleanup behavior.
- Every running ability must be removable on death, logout, dimension change,
  character change and server stop.
- Never create a new networking format if an existing payload can be extended safely.
- Reuse AbilityEngine, Timeline, VFXEngine, Targeting and CooldownManager.
- Do not duplicate cooldown, cost, target or cleanup logic inside individual abilities.
- Every ability must define its conflicts with other abilities.
- Every ability must define its server state and client visual state separately.
- All configurable gameplay numbers must come from CharacterConfig.
- Use game ticks internally; convert to seconds only for display and documentation.
Renderingregels
Text
## Rendering rules

- Use ConstructPainter/VFXEngine instead of creating a separate renderer per ability.
- Cache static mesh data and bounding information.
- Reuse vertex buffers and temporary arrays where practical.
- Use frustum culling for every large effect.
- Use distance-based level of detail.
- Do not send vertices over the network.
- Send compact state: id, position, direction, age, size, shape and animation state.
- Every effect must have first-person and third-person behavior defined.
- Every custom mesh must define bounds and a low-detail fallback.
- Use RenderType batching instead of one draw call per small element.
Qualityregels
Text
## Quality rules

- Do not call an ability complete until gameplay, visuals, sounds, first-person,
  third-person, multiplayer and cleanup are tested.
- Match the design document exactly unless a deliberate change is documented.
- Never replace a detailed effect with placeholder particles without explicit approval.
- Reuse existing visual language: easing, glow, solid hard-light geometry and animation timing.
- Every new ability needs a documentation entry and changelog entry.
- Test at normal speed, slow motion and with multiple nearby players.
- Test in a cave, outdoors, in water, while flying and near blocks.

Ja. De mod heeft al een soort custom engine, maar die is nu nog vooral een verzameling gespecialiseerde systemen. De belangrijkste volgende stap is om die systemen om te bouwen tot één globale Multiverse Powers Engine die niet afhankelijk is van Green Lantern, Doctor Octopus of één specifieke ability.

Niet letterlijk 100× sneller in FPS of development — dat kan niemand garanderen — maar architectonisch kan het systeem wel vele malen krachtiger, herbruikbaarder en sneller worden.

3. Wat een globale engine betekent
Een globale engine betekent dat elke character en ability dezelfde kernsystemen gebruikt.

Niet:

Green Lantern heeft zijn eigen rendering, timing, energy, cleanup en packets.

Maar:

Alle characters gebruiken dezelfde algemene engine. Green Lantern levert alleen zijn eigen data, modellen, abilities en presentatie aan.

De engine wordt dan een platform waarop content draait.

25. Wat je niet moet doen
Een grotere engine betekent niet dat je alles zelf moet vervangen.

Niet verstandig:

Een complete eigen game loop bouwen
Minecrafts renderer volledig vervangen
Een volledige nieuwe physics engine maken zonder noodzaak
Alles in één enorme superclass stoppen
Elk effect als entity maken
Voor elk klein effect een apart packet maken
Alles per character dupliceren
Alle visuals server-side proberen te berekenen
Alle data volledig in Java hardcoden
Iedere toekomstige feature alvast over-abstraheren
Performance optimaliseren zonder profiling
Claude toestaan om architectuurregels te negeren
Een systeem bouwen dat alleen Green Lantern begrijpt
De engine moet uitbreidbaar zijn, maar niet onnodig ingewikkeld.

Is de huidige structuur “slecht”?
Niet per se.

Voor de huidige fase is het logisch:

Er zijn nog maar twee echte characters.
Green Lantern is het grootste systeem.
De code is nog volop in ontwikkeling.
Veel bestanden horen functioneel bij Green Lantern.
Maar voor de geplande toekomst is het wel:

Te veel character-specifiek
Te weinig globale scheiding
Moeilijker herbruikbaar
Moeilijker te testen
Moeilijker voor Claude om correct uit te breiden
Gevaarlijker zodra tientallen characters worden toegevoegd
De structuur is dus niet “waardeloos”; hij is vooral nog niet voorbereid op de uiteindelijke schaal van de mod.

Beste overgang
Niet alles in één keer verplaatsen. Dat kan veel bugs veroorzaken.

Een veilige migratie is:

Maak een nieuwe engine/-laag.
Verplaats eerst volledig generieke classes.
Laat tijdelijke compatibiliteits-wrappers bestaan.
Bouw één algemene VFX-interface.
Migreer eerst Green Lantern.
Migreer daarna Doctor Octopus.
Gebruik spells als derde test.
Voeg pas daarna nieuwe characters toe.
Verwijder oude character-specifieke duplicatie wanneer alles werkt.
Green Lantern en Doctor Octopus zijn goede testcases omdat ze heel verschillend zijn:

Green Lantern test rendering, beams, flight en constructs.
Doctor Octopus test tentacles, grabbing, climbing, portals en custom movement.
Spells testen projectile-, area-, status- en timed effects.
Als de engine deze drie goed ondersteunt, is hij waarschijnlijk echt globaal bruikbaar.

24. Wat “47,8% sneller” dan realistisch kan betekenen
Een getal zoals 47,8% is geen bewezen resultaat zolang er geen benchmark is.

Het kan verschillende dingen bedoelen:

Development speed
Een character bouwen duurt minder lang omdat systemen herbruikbaar zijn.

Bijvoorbeeld:

Oude situatie: veel weken voor een complexe character
Nieuwe situatie: minder tijd omdat movement, resources, abilities, animations en VFX al bestaan
Debug speed
Een bug in cooldowns hoeft niet in twintig characters apart te worden opgelost.

Content speed
Een nieuwe beam of projectile kan worden gemaakt met bestaande engine-bouwstenen.

Runtime speed
Caching, pooling, culling en batching kunnen de runtime verbeteren, maar het percentage hangt af van:

Aantal spelers
Aantal actieve effecten
Mesh complexity
Distance
Hardware
Minecraft settings
Andere mods
Modded world complexity
Dus 47,8% kan een doel of schatting zijn, geen garantie.
